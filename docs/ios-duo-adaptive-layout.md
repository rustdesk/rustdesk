# Adaptive iOS remote-session layouts

## Requirements and references

Remote sessions should use the complete iPhone Duo window in outer portrait, outer landscape, unfolded portrait and unfolded landscape. A horizontal half-fold keeps native text input below the division. The upper area holds the remote image. When native input is hidden, all session floating controls use the lower area; when it is visible, the same controls use the upper area above the keyboard. Within that active area, auxiliary keys remain at the top, the toolbar at the bottom, and chat and mouse controls retain their usual relative placement. Pinned auxiliary keys or selected touch modifiers remain visible when the toolbar is collapsed. Fit must preserve the remote aspect ratio; its letterboxing is separate from an app compatibility window or unused safe-area bands.

Ordinary layouts retain the existing toolbar placement, user scaling/panning and keyboard offset restoration. Entering a ready half-fold remote session requests the native keyboard once. Native Return retains the ordinary remote Enter behavior. A half-fold-only native-keyboard toggle in the blue toolbar opens or dismisses native input. The original auxiliary-key control toggles auxiliary keys only, so native input and auxiliary keys have distinct controls. Keyboard dismissal returns the controls to the lower area with the toolbar expanded by default; keyboard opening moves them above the keyboard with the toolbar initially collapsed. Chat retains its original multiline Return behavior and explicit Send button. Dismissing native input preserves its draft.

- [Apple full-window guidance](https://developer.apple.com/iphone-duo/prepare/)
- [UIHingeInteraction](https://developer.apple.com/documentation/uikit/uihingeinteraction)
- [Flutter scene migration](https://docs.flutter.dev/release/breaking-changes/uiscenedelegate)

## Design choices

Use the official Flutter scene/implicit-engine entry point and current-view native geometry. Keep the existing RemotePage route, session, input protocol, text controllers and controls. iOS uses a separate layout entry point so the established non-iOS body remains intact.

The render surface extends to the window edges. Foreground controls apply their own safe-area handling; the physical outer camera remains an occlusion. A division's interaction margins are not a permanently undisplayable band. Read the division frame/margins and keyboard intersection rather than assuming a fixed hinge or keyboard size.

Rejected alternatives:

- An input accessory stays directly above the system keyboard and does not reduce its reserved frame; use independent top-aligned auxiliary keys instead.
- Default stretching, cropping or changing the remote host's physical resolution changes visible content rather than fixing the local window.
- A new fixed keyboard scale floor or additional scale/offset caches duplicates existing canvas state and changes ordinary input behavior.

## Architecture and regression surface

**Native lifecycle.** AppDelegate registers plugins through the implicit-engine callback; RustDeskSceneDelegate attaches a transparent, non-interactive geometry observer to the active root view. One event channel reports view bounds, hinge status, active division frames/margins and the keyboard intersection in view coordinates. New hinge/reserved-region APIs are guarded by iOS 27.1 availability. Flutter deep-link routing is disabled so the existing uni_links path continues handling RustDesk links. Status-bar appearance is controlled by the view controller.

**Layout.** RemotePage enters half-fold mode only for a partially open, horizontal, active division matching the current window dimensions. This rejects closed-device divisions and stale geometry during rotation. The upper image reaches the division's core boundary; controls use the lower interaction boundary while the keyboard is hidden. If the keyboard overlaps the upper boundary, the image uses the keyboard's actual top. A persistent bounded Overlay moves as a whole between the lower area and the available upper area. Its size and zero keyboard inset match that active area, so chat and dialog entries move with the same owner without applying keyboard avoidance a second time. The base entry is transparent and leaves remote-image taps available outside controls; only the toolbar row has a small Scaffold for BottomAppBar geometry. Authentication uses the global overlay because it can precede the lower layout.

**Canvas and input.** WindowMetricsWatcher reports the real body viewport to CanvasModel. Registered iOS viewports use the same zero-padding origin for drawing and pointer conversion; pages without a registered viewport retain their original padding. Lower-pane controls do not subtract space from the upper canvas. Android action-overlay initialization uses the same ready/first-image condition as the original mobile layout, with the overlay attached to the session's bounded control area.

Half-fold virtual mouse controls use the active control area with matching inherited dimensions. Their normal center and bottom-relative placement is retained; left/right buttons use deterministic positions without reading or saving ordinary fullscreen position preferences. Half-fold control rectangles are excluded from the separate canvas hit test; active drag/scroll blocking remains in effect. Touch-mode mouse movement uses relative deltas rather than treating a lower-pane global position as an upper-canvas pointer position.

**Keyboard and user position.** Window/DPR changes refit the image. Ordinary keyboard resizes update viewport dimensions without refitting, retaining the existing scale/offset save, cursor avoidance and restoration. Keyboard detection reads the FlutterView's raw inset because Scaffold consumes the inherited MediaQuery inset. Preserve isMobileCanvasChanged for registered iOS viewports during keyboard input so a later toolbar toggle does not discard the restored user position. Half-fold keyboard changes may refit the upper image. Session clear resets the viewport, division flag and iOS adjustment flag.

**Chat.** The existing chat-window entry point suppresses automatic keyboard requests whenever controls are outside the canvas. This covers the toolbar, floating chat icon and incoming-message paths. Ordinary chat keeps its multiline configuration. Half-fold chat retains its original multiline Return action; sending remains explicit.

**Half-fold keyboard controls.** Keep one control widget in the persistent Overlay base entry. The Overlay's position and MediaQuery change with the actual native keyboard frame, rather than keeping separate upper and lower owners or special chat-only full-window bounds. Its auxiliary-key control requests the existing KeyHelpTools without changing native keyboard visibility. Collapsing the toolbar hides unpinned auxiliary keys; KeyHelpTools retains its pin, compact/Fn selection and visible touch modifiers across native-keyboard toggles. The auxiliary area follows the original top placement, applies its own safe area and scrolls within the active area without resizing the remote image. Native-keyboard transitions reset only the existing toolbar-expanded flag to the deterministic default for the current state.

Native input opens on first image or a transition into half-fold only when keyboard input is already permitted. Explicit opening retains the original permission gate; automatic entry does not reopen a warning the user declined. Frame updates and explicit dismissal do not reopen it automatically. The additional toolbar button opens native input with the existing openKeyboard path or dismisses it with the ordinary focus steps, including chat unfocus. It does not send a remote key. The previous lower Keyboard row and FAB-adjacent hide button are removed. Ordinary toolbar keyboard/FAB behavior is unchanged.

The legacy floating chat icon reads full-view dimensions internally. Its half-fold-only configuration uses the active area's origin and bottom boundary, accounting for the upper origin when the keyboard is visible. Recreate only that icon when the active area's size or keyboard state changes; chat-window entries and their controllers remain mounted. Ordinary chat-icon configuration remains unchanged. Manual chat-window dragging outside the screen is pre-existing and is not replaced by a new generic positioning subsystem.

**Builds.** iOS uses Flutter 3.44.8, an SDK providing iOS 27.1 APIs, and the existing Flutter 3.44 bridge-artifact path. The shared source-patch script supports BSD sed on macOS while retaining GNU sed behavior for Windows arm64. Other platform Flutter versions remain unchanged. No remote protocol, generated bridge interface, audio or file-transfer behavior is changed.

Confirmed regressions and fix rationale:

- Whole-page SafeArea plus canvas padding left unused edge bands; using a real body viewport also prevents counting the bottom toolbar as displayable image space.
- Treating every body resize as Fit discarded normal keyboard/user positioning. Distinguish window changes, keyboard changes and ordinary viewport changes; preserve the existing adjustment flag through keyboard restoration.
- The separate iOS entry point omitted Android action-overlay initialization. Restore the original ready/first-image condition rather than adding a second overlay lifecycle.
- Replacing a keyed Overlay lost entries after authentication; retaining one entry and rebuilding its child preserves session controls. An added opaque middle layer swallowed first clicks and drags, so it is removed.
- Restricting chat keyboard suppression to the toolbar left floating-icon and incoming-message paths inconsistent. Apply the policy once at the shared chat-window entry point.
- The floating chat widget's full-view origin placed its icon outside the lower overlay. Use its existing non-fullscreen offset for half-fold coordinates rather than adding position state.
- The OS Password edit icon assumed its menu was a Navigator route and popped the remote page from the half-fold overlay. Give only that menu an explicit tagged dismissal callback; ordinary popup menus retain their existing dismissal path.
- Virtual mouse widgets inherited lower-pane dimensions inside a shorter fixed box, clipping the wheel/buttons and confusing lower-local blocking rectangles with upper-canvas coordinates. Match the active-area dimensions and isolate half-fold positions from ordinary saved positions. The virtual-mouse layer is absent while disabled, removing the PR-added blank space above gesture help.
- Hiding half-fold controls and auxiliary keys behind the native keyboard made combination-key input inaccessible. Move the same auxiliary instance and other floating controls to the available upper area while the keyboard is visible, expose the toolbar on request, and give native input a distinct toolbar toggle. Reuse the original modifier and pin behavior rather than duplicating key state. The native keyboard owns its size; a custom inputView would replace that keyboard.

The user identified a further input regression before publication: substituting `TextInputAction.done` for native Return removed the newline consumed by the existing remote-input path, so the peer received no Enter. The same override removed chat line breaks. Restore both original TextField configurations and remove the Done submission callback. A half-fold-only native-keyboard toggle in the existing blue toolbar uses the ordinary keyboard-open/dismiss paths, preserving the separate auxiliary-key control. The earlier display/keyboard-toggle matrix did not cover native Return semantics and cannot establish this regression is fixed. Final acceptance must include exactly one delivered native Enter, chat multiline input, explicit keyboard dismissal without a spurious key, composition behavior and the same-binary matrix.

## Delivery and validation contract

Implementation and review are scoped to this feature's final diff. Runtime changes require the complete simulator matrix: five Duo postures by twelve distinct remote ratios, followed by iPhone 18 Pro portrait/landscape by the same twelve ratios. Ratios are 16:9, 16:10, 3:2, 4:3, 5:4, 43:18, 32:9, 9:16, 9:20, 20:9, 3:4 and 1:1; identical ratios at different pixel counts are not separate cases.

Each case uses a real RustDesk peer and checks the remote framebuffer/decoded size, complete fitted image, five delivered pointer events, keyboard opening/dismissal and canvas restoration. Ordinary cases preserve scale; half-fold cases also check upper-image geometry with the keyboard visible, recording intentional floating-button coverage separately from image clipping. Explicitly expanded toolbars and auxiliary keys intentionally cover part of the image. Supplementary regressions cover user adjustment followed by keyboard round-trip and toolbar toggling, session reconnect, and half-fold chat entry paths. Keep bulk screenshots, logs, build identities, automation and successful-run references outside version control.

Simulator verification is the current acceptance boundary. Physical Duo/15 Pro testing, floating/split/hardware keyboards, two-finger gestures, reverse landscape, iPad multitasking, other pages' status bars, remote Chinese delivery and signed release/CI builds are separate checks. A portrait desktop framebuffer verifies a phone aspect ratio rather than a mobile remote OS. The earlier simulator artifact used environment-only native-library compatibility work and an iOS 15 deployment override. The refreshed base itself now declares iOS 15; this still does not establish older-device support or signed distribution. No release schedule or physical-device sign-off is assigned here.

Known limits:

- The docked system keyboard can cover the entire half-fold lower area. Session floating controls now use the upper area while it is visible. The existing OS Password editor now shares this active-area behavior: its previously obscured input and Cancel action are above the docked keyboard, and cancellation retains the session. Higher keyboards may reduce the available upper area enough to clip a previously dragged chat window; ordinary drag limits remain unchanged. A default upper chat composer and a general dialog/input redesign remain outside this change.
- After switching from half-fold to the closed outer display, the ordinary floating chat icon can be outside the visible window. Its legacy widget reads implicit inner-view dimensions; the half-fold offset fix deliberately leaves the ordinary configuration intact. Toolbar chat remains accessible. Returning to half-fold restores the icon without losing the draft. A general floating-widget geometry replacement is outside this change.
- Half-fold size or keyboard-state changes recreate only the floating icon, resetting its dragged position. Its drag boundary can overlap the toolbar, as in the existing fullscreen behavior. The existing chat window permits manual dragging outside its bounds; no generic clamping rewrite is included.
- The incoming-message chat path is source-reviewed but not runtime-accepted: the dedicated Linux peer's connection-manager process exited before registering a connection. Toolbar and floating-icon entry, native Chinese composition and historical Done cycles were exercised separately; those checks do not establish incoming-message delivery.

Chinese Pinyin remains a separate input limitation. With the same Linux/X11 peer, entering nihao and pressing native Return three times produced cumulative additional discrete Return counts of 0, 0, 1 in both half-fold and ordinary iPhone layouts. A cached pre-migration SDK 26.5 / Dart 3.5.4 binary reproduced the same sequence; its kernel embeds the same iOS text-diff function and has no half-fold entry point. Its exact historical Git revision was not recovered, so this is a historical binary control rather than a pinned-base rebuild. The comparison does not establish Unicode delivery or text-editor line-break behavior. Preserve the existing shared input path in this layout PR instead of adding a speculative IME rewrite.
